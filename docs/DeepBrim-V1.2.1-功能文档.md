# DeepBrim V1.2.1 功能文档

> 版本：v1.2.1（manifest 同步）
> 平台：Microsoft Edge · Manifest V3
> 文档范围：仅记录 **v1.2 之后** 的增量改动
> 文档日期：2026-11-01

---

## 一、版本概览

v1.2.1 是一次**稳定性修复**，不新增界面，集中解决三类问题：

1. 新对话没有历史数据时，请求会空转到 30 秒超时
2. 新对话首轮出现 `0 token` 展示
3. 新对话的自动落库校准从未生效，导致"本轮"不更新

另外修复了一个跨会话数据串台的竞态缺陷。

---

## 二、新对话：快速截断

### 2.1 问题

`hardRefreshHistory` 在拿不到会话 ID 时直接 `return`，但前端不知道结果，`pendingHardRefresh` 一直为真，转圈持续到 30 秒兜底超时。

### 2.2 三个出口全部即时收尾

| 情况 | 行为 | 提示 |
|------|------|------|
| 无会话 ID | 立即返回 `no-session` | 新对话暂无历史，发送消息后自动统计 |
| 增量 `MERGE` 且 0 条、无缓存 | 立即返回 `empty`，不再触发全量 | 该会话暂无历史数据 |
| 全量返回 0 条消息 | 立即返回 `empty`，跳过"请求头复放" | 该会话暂无历史数据 |

三种情况都会停止转圈、清除 `pendingHardRefresh`，响应在几百毫秒内完成。

## 三、0 值防护

### 3.1 问题

新对话早期 SSE 帧可能上报 `accumulated_token_usage = 0`；空历史或全空文本估算也会得到 0。这些 0 被当成有效值后，圆盘显示 `0 token`。

### 3.2 四层拦截

| 层 | 规则 |
|----|------|
| SSE 解析 | `accumulated_token_usage <= 0` 的占位帧直接忽略 |
| 历史回补 | 基线 ≤ 0 一律视为无效（含估算结果为 0），置为 `null` |
| 内容层 `usage` / `stream-end` | 只接受大于 0 的总量 |
| 内容层 `history-baseline` | 只接受大于 0 的基线；`baselineSource` 同步置空 |

显示规则：无有效值时圆盘显示 `—`，不会出现 `0`。

## 四、新对话自动落库校准

### 4.1 问题

v1.2 的 `syncAfterTurn` 要求"上一次历史请求属于同一会话"。新对话从未发起过历史请求，条件不成立，校准被直接跳过，导致：

- 总量停在本轮请求时的上下文值
- 「本轮」一直显示 `—`
- 用户必须手点「重新拉取历史」才能更新

### 4.2 现在的策略

```
生成结束（延迟 600ms）
  ├─ 有同会话模板 → 增量请求（毫秒级，8s 超时）
  └─ 无模板（新对话） → 全量请求（4s 超时）
```

两条路径共用同一套落库校准逻辑：

- 取 `current_message_id` 那条消息的累计值作为总量
- 本轮 = 本次总量 − 上次总量，**仅在总量向前增长时成立**
- 推送 `post-turn`，更新圆盘、缓存与上一轮基准

### 4.3 增量模板沉淀

新对话走全量时，如果响应里带回 `cache_version` / `cache_reset_at`，会自动生成一份增量模板，后续轮次回到毫秒级增量路径。

日志：`🗂 已沉淀增量模板 cache_version=...`

### 4.4 延迟与正向判定

- 校准统一延迟 600ms，避免服务端尚未落库时读到旧快照
- `roundTokens` 仅在 `total > before` 时计算；0 或负数视为未落库，不覆盖已有本轮值

## 五、跨会话数据隔离（竞态修复）

### 5.1 问题

`handleData` 收到任何 payload 时，只要 `sessionId` 与当前不同就调用 `switchSession()`。真实故障：

- 在会话 A 发消息后立刻切到 B，A 的流式 `usage` 或延迟执行的 `post-turn` 到达时，界面被强行切回 A
- 落库校准与用户切会话存在竞态，圆盘短暂显示错误会话的数字

### 5.2 修复

```js
if (!state.sessionId) switchSession(incoming)
else if (incoming !== state.sessionId) return
```

- 只有当前没有会话（新对话首条消息）时才接管
- 其他会话的后台数据一律丢弃，不改变界面

## 六、流量与耗时

| 场景 | 请求 | 耗时/体积 |
|------|------|-----------|
| 老会话每轮校准 | 增量 | 100–300ms，约 18KB |
| 新对话每轮校准 | 全量 | 通常 < 500ms（消息少），4s 超时上限 |
| 新对话手动刷新 | 无请求 | 立即返回提示 |
| 有模板后的后续轮次 | 增量 | 同第一行 |

## 九、已知限制

1. 新对话全量校准上限 4 秒；若会话异常庞大且没有模板，本次校准会被放弃（下次轮次继续尝试）
2. 新对话每条消息仍会多一次全量请求，直到沉淀出 `cache_version`
3. 首轮「本轮」固定为 `—`，因为没有上一轮落库总量作差
4. 仍未提供扩展图标资源
